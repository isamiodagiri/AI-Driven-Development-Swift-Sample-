# 05 設計裁定と未解決事項

> **正**: 「なぜそう決めたか」。実装中に判断が要るとき、まずここを見る。
> **★** が付いた項目は**ユーザー未確認**（＝ 設計側の判断）。★ なしはユーザーが直接決めたもの。

---

## 1. 裁定

### D-1. モジュールは SPM で分割する（ユーザー裁定 2026-09-05）

Flutter 側の pub workspace ＋ カスタムLint に相当する強制を、**SPM のターゲット依存**で得る。
単一ターゲット＋フォルダ分割は、層をまたぐ参照をビルドが止められないため採らない。

### D-2. ★ Entity は `Repo`、層は `Repository` と呼ぶ

GitHub の "repository" と層名 Repository が衝突する。**Entity 側を短縮**して
`Repo` / `RepoSummary` / `RepoDetail` とする。`RepoRepository` は読みにくいが、
**層の名前を曲げると規約の判定根拠（命名）が壊れる**ため、こちらを採る。

- 採らなかった案: 層を `DataStore` / `Gateway` と呼ぶ → 依頼された4層の名前から外れる
- 採らなかった案: Entity を `GitHubRepository` にする → `GitHubRepositoryRepository` になる

### D-3. 境界は `async/await`、出力は Combine（ユーザー裁定 2026-09-05）

詳細と、採らなかった2案は [01 §5](01-architecture.md#5-並行性swift-concurrencyと-combine-の分担-本pjの中核)。
**Repository が `AnyPublisher` を返す形は採らない**（`Sendable` / actor と噛み合わず、
`@unchecked Sendable` ゼロという評価軸を守れないため）。

### D-4. ★ Feature は画面ごとに別ターゲットにする

「Feature 同士を参照しない」をコンパイラに守らせられるのは分割した場合だけ。
kotoba-album（1パッケージ）ではなく ChildAsset（複数パッケージ）の方式を採る。

### D-5. ★ お気に入りは ID ではなく `RepoSummary` ごと保存する

ID だけを保存すると、お気に入り一覧を開くたびに N 件の詳細 API を叩くことになり、
**未認証の 60 req/時を1画面で使い切る**。表示に必要な情報を丸ごと持つ。
**代償**（保存した内容が古くなる）は受け入れる — 詳細を開けば最新が取れる。

### D-6. ★ テスト専用も含めて外部依存を入れない

読者が `swift test` を打つまでの障害を無くすため。
**ただし実PJでは `combine-schedulers`（debounce の決定的テスト）と
`swift-snapshot-testing` を入れる判断が妥当**であり、README にそう明記する。
本サンプルは「入れないほうが良い」とは主張しない。

> **この裁定は [D-18](#d-18--viewinspector-を1つだけ入れるユーザー裁定-2026-09-06) で
> 一部を撤回した。** テスト専用の依存を1つ（`ViewInspector`）だけ入れる。

### D-7. ★ アプリ本体は空に近い Xcode プロジェクト、実体はすべて Package

`swift test` が Xcode 無しで回ることを優先する（CI が速く安定する）。
Xcode プロジェクトが持つのは `App.swift` / `CompositionRoot.swift` / `AppRouter.swift` の3つだけ。

### D-8. ★ UseCase の protocol は作らない

ViewModel は UseCase の**具体型**を受け取る。UseCase は `Sendable` な `struct` で、
依存が Repository の protocol なので、テストは Repository のスタブで足りる。
**ダブルの層を1つ増やすと、実物とずれる箇所が1つ増える**（参照元PJで実測された事故の形）。

### D-9. ★ State は排他な `enum` を持ち、独立したフラグを並べない

`isLoading` / `error` / `items` を別々に持つと「ローディング中かつエラー」という
**表現できてはいけない状態**が型の上に存在してしまう。[01 §7-2](01-architecture.md) の形にする。

### D-10. ★ キャンセルとは別に「世代番号」を持つ

`cancel()` はネットワーク完了後には間に合わない。**古い応答が新しい結果を上書きしない**ことは
世代番号でしか保証できない（[01 §5-4](01-architecture.md)・AC-17）。
**両方要る**（片方だけだと、実装は一見正しく、テストも偶然緑になる）。

### D-11. 未認証を既定とし、トークンは任意（ユーザー要件「Public 情報取得」より）

トークンを埋めた配布物は本番では不可であることを README に明記する（[02 §5](02-github-api.md)）。

### D-12. ★ テストフレームワークは Swift Testing

Swift 6 / iOS 17 前提であり、`#expect` の失敗表示が読みやすい。
XCTest は**スナップショットや UI テストを足す段になったら併用**する（排他ではない）。

### D-13. ★ View のテストは3項目に限定する（[04 §3](04-test-strategy.md)）

View を厚くテストすると、レイアウトを変えるたびにテストが落ちて**壊れていないのに赤になる**。
「State に出ているのに画面に出ていない」だけを狙う。

### D-14. ★ iOS 17 / Swift 6 language mode / strict concurrency = complete

`@Observable` ではなく `ObservableObject` を使うのは D-3（出力は Combine）の帰結であり、
iOS のバージョン制約によるものではない。

### D-15. 同じ層のもの同士の参照を禁じ、SwiftLint で守る（ユーザー裁定 2026-09-05）

**View は1つの ViewModel だけを参照する／View はロジックを持たない／ViewModel・UseCase・Repository は
それぞれ同種のものを参照しない**（INV-9〜INV-13）。
縦の依存は SPM が落とすが、**横の参照は同一ターゲット内なのでコンパイラに見えない**ため、
**SwiftLint の `custom_rules`** が検査する（[01 §9](01-architecture.md)）。

- **なぜ Lint にしたか**: レビューで守る規約は、レビューする人が変われば守られなくなる。
  参照元PJの「レビューではなくカスタムLintが機械的に強制する」方針をそのまま採る
- **なぜ SwiftLint か（自前スクリプトや `swift-syntax` ではなく）**:
  ① Swift の標準的な Lint であり、**Xcode に警告として出る**（CI まで待たない）
  ② `custom_rules` は**ファイル全体に正規表現をかけられる**ので、
  「異なる型が2つ以上現れる」＝「自分以外を参照した」を後方参照で表現でき、
  **INV-9〜INV-13 が追加のコードなしで書けた**（[01 §9-2](01-architecture.md)）
  ③ 導入が `brew install swiftlint` と YAML だけで済む
- **`swift-syntax` ベースのルールは採らなかった**（現時点では）:
  正確さでは勝るが、ビルド対象のツールを1つ抱えることになり、M1 の初日から動かない。
  判定内容を [01 §9-1](01-architecture.md) の表に固定してあるので、**必要になったら実装だけ差し替えられる**
- **INV-10 は近似である**ことと、**`match_kinds` を使えない代償**（コメント・文字列の中でも発火する）を
  [01 §9-3](01-architecture.md) に明記した。**検査が全部を見ていると誤解されるほうが危険**である
- **ルールには検収を付ける**（`scripts/test-lint-rules.sh`）。空振りしているルールは CI では緑に見えるため。
  実際に INV-6 の穴が1件この検収で見つかっている

> **経緯**: 初版では自前の bash スクリプト（`scripts/check-architecture.sh`）で実装したが、
> 「Swift にも Lint があるのだから、そちらで検知したい」というユーザーの指摘を受けて
> SwiftLint へ一本化し、bash 版は削除した（同じ判定を2箇所に持たないため）。
> 検収の仕組み（違反注入）はそのまま引き継いでいる。

### D-16. 整形は **SwiftFormat**（nicklockwood）に一本化する（ユーザー裁定 2026-09-05）

- **フォーマッタは1つしか置けない。** 2つ入れると互いに整形し合い、保存のたびに差分が出続ける。
  「SwiftFormat も入れてほしい」という指示に対し、**SwiftFormat を採用し、
  Apple の `swift-format` は外した**（併存させる形は成立しないため）
- **なぜ SwiftFormat か**: 設定できる範囲が広く（`--self remove`・`--wraparguments` 等）、
  SwiftLint と組み合わせる構成が広く使われていて情報が多い。
  `brew install swiftformat` の1行で入る
- **代償**: Apple の `swift-format` と違い**ツールチェーンに同梱されていない**ので、
  導入が1つ増える（D-6「外部依存を入れない」は SwiftPM の依存についての方針であり、
  開発ツールの CLI はその対象外と整理した）
- **重複は必ず片方に寄せる**（[01 §10-1](01-architecture.md)）。
  `line_length` を両方に置くと、片方だけ変えたときに永久に赤が出続ける
- **`--swiftversion 6.0` を明示する**（省略すると推測になり、環境ごとに結果が変わる）
- **CI は整形しない**（差分があれば落とすだけ）。CI が push すると手元と履歴がずれる

> **経緯**: 初版は Apple の `swift-format`（ツールチェーン同梱・追加導入なし）を採っていたが、
> ユーザーの指示で SwiftFormat へ差し替えた。**採用理由が「追加導入が要らないこと」だったので、
> その根拠は失効している** — 代わりに設定の自由度と情報量を採ったことを、上に書き直した。

### D-17. 不変条件のほうが口の形を決めることがある（2026-09-05・実装で判明）

`KeyValueStore`（端末内保存の口）を**同期**にすると、テスト用の実装が
「ロックを持ち、チェックを外して `Sendable` を名乗るクラス」になり、**INV-4 に違反する**。
そこで**口を `async` にした**。`actor` で実装できるようになり、違反が消えた。

- 順序が逆であることに意味がある。**「テストが書きにくいから設計を変えた」のではなく、
  「不変条件を守れない設計だと分かったから変えた」**である
- 同じことが `RepoRowDisplay` でも起きた。**View は Domain を参照できない**（INV-5）ので、
  詳細画面が「取得に失敗した状態でお気に入りに保存する」には、
  表示用の値が素の件数を持っている必要があった（[04 §7-2](04-test-strategy.md) TS-71）。
  持たせないと、保存した件数が 0 に化ける
- **不変条件は制約であると同時に、設計の検出器でもある**

### D-18. ★ ViewInspector を1つだけ入れる（ユーザー裁定 2026-09-06）

**Q-1 の裁定。** [D-6](#d-6--テスト専用も含めて外部依存を入れない)を一部撤回し、
**テスト専用の外部依存を1つだけ入れる**（`nalexn/ViewInspector`）。
`swift-snapshot-testing` は採らない。

- **理由**: 未実装だった 16 件はいずれも「**State に出ているのに画面に出ていない**」
  を狙うものである（[04 §3-1](04-test-strategy.md)）。依存ゼロを守ることより、
  **この欠落を検出できることのほうが、このサンプルが示したい規律に近い**
- **絵ではなく要素の有無で見る理由**: 16 件のうち3件（TS-51・TS-52・TS-76）は
  **クロージャが呼ばれることの確認**であり、スナップショットでは観測できない。
  スナップショットは**レイアウトを変えるたびに全件が赤になる**（[D-13](#d-13--view-のテストは3項目に限定する04-3)の逆をやることになる）
- **持ち込む範囲を限る**: 依存は3つの Feature のテストターゲットにだけ書く。
  `Sources/` からは見えない（`Package.swift` が強制する）

### D-19. ★ Dynamic Type は AX3 まで、VoiceOver はラベルまで（ユーザー裁定 2026-09-06）

**Q-3 の裁定。** `.accessibility3` まで文字を拡大しても**各画面が読める**こと
（行の折り返しで対応し、切り詰めない）。VoiceOver は
**アイコンだけのボタン（☆ / ★・「GitHub で開く」）と、数値バッジにラベルを打つ**。
`.accessibility5` までは追わない — レイアウトを大きく組み替えることになり、
**サンプルとしての読みやすさが落ちる**ほうの損が大きい。

### D-20. ★ 文言は日本語固定（ユーザー裁定 2026-09-06）

**Q-4 の裁定。** String Catalog は入れない。
文言は既に `DesignSystem`（`AppErrorState`）と `Presentation` に集約してあるので、
**ローカライズが要るようになった時点で、そこだけを差し替えれば足りる**。
このサンプルの主題は層構造であり、**話題を増やさない**。

### D-21. ★ ダークモードのために色を2系統持たない（ユーザー裁定 2026-09-06）

**Q-2 の裁定。** 明暗で切り替えるトークンを別に用意しない。

`AppColor` は既に**システムのセマンティックカラー**（`Color.primary` / `.secondary` / `.accentColor`）と
**グレーの不透明度**だけで組んであり、**明暗の切り替えは OS 側が行う**。
ここに明用・暗用の2系統を足すと、**同じ色を2箇所で決めることになり、片方だけ直る**。

> **「破綻しないはず」であって、「確かめた」ではない。**
> 明暗それぞれの見た目は誰も見ていない（[04 §3-1](04-test-strategy.md) と同じ理由で、
> `@Environment` の `colorScheme` はテストから差し替えられない）。
> 実PJでダークモードを保証するなら、**スナップショットか目視の受け入れが要る**。

### D-22. ★ 検索のソート / 言語フィルタは足さない（ユーザー裁定 2026-09-06）

**Q-5 の裁定。** UC-001 の AC-15 が固定している既定（`stars` 降順）のままとし、
並び替えや絞り込みの UI は作らない。**このサンプルの主題は層構造であり、機能の幅ではない。**

### D-23. ★ リポジトリの公開はしない（ユーザー裁定 2026-09-06）

**Q-6 の裁定。** 新しいリポジトリは作らない。
既にある `isamiodagiri/AI-Driven-Development-Swift-Sample-` をそのまま使い、公開範囲も変えない。

> **一度、事実と違うことを書いた。** この裁定を最初「ローカルに置いたままとする」と書いたが、
> **`git remote` には既に origin があった**。確かめずに「新しく作らない ＝ 置き場が無い」と
> 読み替えたのが誤りである。**裁定は、確かめられる事実の上に書く。**
> 直接の影響として、`.github/workflows/ci.yml` は**動く場所がある**（GitHub Actions で回る）。

### D-24. ★ Xcode プロジェクトは XcodeGen で生成する（2026-09-06・実装で判明）

**`.xcodeproj` を作る手段**を、手作業から **XcodeGen（`App/project.yml`）** に変えた。
[D-7](#d-7--アプリ本体は空に近い-xcode-プロジェクト実体はすべて-package)（生成物をコミットしない）は変えていない。

もともと `App/README.md` に「Xcode で新規プロジェクトを作り、ローカルパッケージを足し、
言語モードを Swift 6 にする」という**5手順の手作業**を書いていた。これには2つ問題があった。

- **手順を踏んだ結果が人によって違う。** 「アプリが動かない」ときに、
  実装の問題なのか手順の取りこぼしなのかが**切り分けられない**
- **設定が文書にしか無い。** `SWIFT_STRICT_CONCURRENCY = complete` を落としても誰も気づかない
  — [D-14](#d-14--ios-17--swift-6-language-mode--strict-concurrency--complete) が
  Package 側でしか効いていない状態になる

`App/project.yml` は**読める YAML** なので、`project.pbxproj` を避けた D-7 の理由をそのまま満たす。

- **道具が1つ増える**（`brew install xcodegen`）。**アプリを起動したい人だけが要る**
  — `swift build` / `swift test` / Lint は今までどおり XcodeGen なしで通る
- 生成物（`App/GitHubSampleApp.xcodeproj`）と `App/.build-xcode/` はコミットしない
- **`App/Sources/GitHubSampleApp.swift` は実ファイルにした**（`.swift.template` をやめた）。
  拡張子が `.swift` でないと**整形も Lint も型検査も一切かからない**ためである
  — 実際、テンプレートのままでは合成ルートの呼び出しが1行も検査されていなかった

> **起動して初めて分かったことが1つある。** 詳細のトピックが `HStack` に入っていて、
> 幅が足りず**縦棒の列**になっていた（[04 §3-1](04-test-strategy.md)）。
> テストは全件緑のままだった。**アプリを一度も起動しない開発は、ここを見落とす。**

## 2. 未解決事項

**2026-09-06 時点で、未解決の事項は無い。**
Q-1〜Q-6 はすべて裁定になった（D-18〜D-23）。

**決まったものは表から落としてある** — 決まった事項を「未解決」の欄に残すと、
どちらが正か読む側に判断させることになる。
新しく決めきれない事項が出たら、ここに Q-7 から採番して足す。

> **未解決事項をコードに残すときは、必ず落ちるテストとセットにする。**
> 参照元PJで「仮決定の印をコードコメントにだけ書き、失敗するテストが無かったため
> 誰にも数えられないまま残った」事故が起きている。本PJでは
> `@Test(.disabled("Q-3 未決"))` ではなく **`#expect(Bool(false), "Q-3 未決")` で赤にする**
> （無効化されたテストは緑の中に埋もれる）。
