# 04 テスト戦略と TS（テストシナリオ）一覧

> **正**: テストの層ごとの分担、テストダブルの方針、TS の一覧と AC との対応。
> **AC 78 件 ／ TS 100 件 ／ 対応漏れ 0 件**（§7 で検算する）。

---

## 1. 使うもの

| 項目 | 決定 |
|---|---|
| フレームワーク | **Swift Testing**（`import Testing`。`@Test` / `#expect` / `#require`） |
| UI（View）のテスト | 主戦場は **ViewModel の State を観測すること**。View は「State を描くだけ」に保つ。**§3 の3項目だけ `ViewInspector` で View を覗く**（[05 D-18](05-decisions.md)・2026-09-06 に改めた） |
| スナップショット | **入れない**。M5 で判断し、`ViewInspector` を採った（[05 D-18](05-decisions.md)） |
| HTTP のスタブ | `TestSupport` の `StubHTTPClient`（`Core.HTTPClient` の実装。**`URLProtocol` の差し替えは使わない**） |
| 固定応答 | 実 API の応答をそのまま切り出した JSON（[02 §6](02-github-api.md)） |
| 外部依存 | **テスト専用の `ViewInspector` が1つだけ**（3つの Feature のテストにのみ。`Sources/` からは見えない。理由は §5-3） |

> **不変条件（INV-1〜INV-13）は TS に含めない。** 層依存は `swift build`、
> 横の参照や View のロジック禁止は **SwiftLint の `custom_rules`** が見る対象であり、
> **そのルールが空振りしていないことは `scripts/test-lint-rules.sh`（違反注入 13 件）が確かめる**。
> TS の一覧に無いことは「検証されていない」ことを意味しない（[01 §9](01-architecture.md)）。

## 2. 層ごとの分担（どの層で何を確かめるか）

| 層 | ここで確かめること | ここで確かめないこと |
|---|---|---|
| **Repository** | DTO のデコード、**HTTP → `GitHubError` の写像**、リクエストの組み立て（URL・ヘッダ）、`hasMore` の材料 | 画面の状態、debounce |
| **UseCase** | 入力の検証、**要求してよいかの判断**（ページング上限）、複数 Repository をまたぐ手順 | HTTP の詳細 |
| **ViewModel** | **状態機械**（初期・読込・成功・0件・失敗）、debounce、キャンセル、**世代管理**、Entity→State 変換、エラー→文言 | JSON の形 |
| **View** | §3 の3項目のみ | ロジック |
| **統合** | お気に入りの変更が**複数の ViewModel へ同時に伝わる**こと | — |

**同じことを2つの層で確かめない。** 例: `hasMore` の算出は Repository（TS-6〜TS-8）、
それを使って「呼んでよいか」を決めるのは UseCase（TS-22・TS-23）で、**ViewModel では確かめない**。

## 3. View をテストする3項目（例外）

「State に出ているのに画面に出ていない」を防ぐため、次の3種類だけは View を立てて確かめたい。

1. **条件付きで消える要素**（説明が `null`・言語が `null`・トピックが空）
   — 「消えるべきものが消えているか」は State だけでは観測できない
2. **タップの結線**（行タップ・☆ タップ・「GitHub で開く」がクロージャを正しく呼ぶか）
3. **スケルトンの行数**（`loading` のとき本当に6行出ているか）

観測は `accessibilityIdentifier` を打った要素の存在で行う。**識別子は DesignSystem 側の
`AppIdentifier` が持つ**（テストと View の両方がそこを見るので、改名しても同時に追随する）。

### 3-1. ★ `ViewInspector` で実装した（2026-09-06）— ただし1件だけ落ちている

[05 Q-1 の裁定（D-18）](05-decisions.md)で **`ViewInspector` をテスト専用に1つだけ入れ**、
未実装だった 16 件のうち **15 件を実装した**。依存は3つの Feature のテストターゲットにだけ書いてあり、
`Sources/` からは見えない（`Package.swift` が強制する）。

観測は `AppIdentifier` の識別子で行う。**テストと View が同じ定数を見る**ので、改名しても両方が追随する。

#### 実装できなかった1件 — TS-94（スワイプで削除）

**`ViewInspector` は `.swipeActions` に対応していない。**
`.swipeActions` は修飾子の中に Button を隠すため、ビューの値ツリーを辿る方式では中身に届かない
（`ViewInspector` 0.10.3 のソースに `swipeAction` の語が1つも無いことを確認した）。

- **これは「テストを書き忘れた」ではなく「この道具では観測できない」である。**
  区別が付くように、TS 一覧の該当行に理由を書いてある
- **削除そのものは別の経路で見えている**: スワイプの Button も ★ の Button も
  同じ `viewModel.remove(rowID:)` を呼ぶので、**削除の振る舞い自体は TS-95 が押さえている**。
  観測できていないのは「**スワイプという入口が結線されているか**」だけである
- 埋めるなら UI テスト（XCUITest）が要る。**Xcode プロジェクトが手作業である**（[05 D-7](05-decisions.md)）
  以上、`swift test` だけで回らなくなるので入れていない

#### この3項目を全部通しても、**崩れ**は見つからない（2026-09-06・実機で判明）

シミュレータで起動して初めて、**詳細のトピックが縦棒の列になっている**のが見つかった。
`HStack` は幅が足りないとき**子を縮める**ので、トピックが1文字ずつ縦に折り返されていた。

- **View テストは全件緑のままだった。** TS-75 は「トピックの行が**在るか / 無いか**」しか見ておらず、
  **在るものがどう並んでいるかは見ていない**
- 直し方は `AppFlowLayout`（入りきらない分を次の行へ送る `Layout`）を DesignSystem に置くこと。
  **`HStack` に可変長の並びを入れない**という話であって、テストの不足ではない
- **教訓**: 要素の有無で見る View テストは、「出ていない」は捕まえるが「**出ているが読めない**」は
  捕まえない。**起動して目で見る工程は、この方式では省けない**

#### Dynamic Type も観測できていない

裁定 [D-19](05-decisions.md) で「AX3 まで崩れない」と決めたが、
**`ViewInspector` は `@Environment` の値を差し替えられない**（`EnvironmentObject` の注入しか持たない）。
そのため `dynamicTypeSize` を大きくした状態は作れず、**縦積みへの切り替えは自動で確かめていない**。
VoiceOver のラベル（TS-101・TS-102）は観測できるので、そちらは入れてある。

## 4. テストダブルの方針

| 方針 | 理由 |
|---|---|
| **スタブは実物より寛容にしない** | 参照元PJで実測された事故: フェイクが実物より緩く、実装の欠落がテストで隠れた |
| **UseCase の protocol は作らない**（ViewModel は具体型を受ける） | ダブルの層が1つ増えるほど、実物とのずれが起きる箇所が増える。UseCase は `struct` なので Repository のスタブで足りる |
| Repository のスタブは**呼ばれた引数を記録する** | 「呼ばれていない」（AC-1・AC-21・AC-24）を観測できる形にする |
| 時刻は注入する（`now: () -> Date`） | 相対表記（AC-13）とレート制限の残り時間（AC-31）を固定するため |
| debounce の間隔とスケジューラは注入する | §5-1 |

## 5. 難しいところの扱い

### 5-1. debounce をどうテストするか

`SearchViewModel` は `init(debounceInterval: DispatchQueue.SchedulerTimeType.Stride = .milliseconds(300), scheduler: DispatchQueue = .main)` を取る。
テストでは `.zero` を渡し、**`await Task.yield()` ではなく期待値の到達を待つ**（`confirmation`）。

- **採らなかった案**: `combine-schedulers` の `TestScheduler` を入れる。
  正確に時間を進められて優れているが、**外部依存ゼロ**という本サンプルの前提を崩す。
  実運用のPJでは入れる価値がある、と README に注記する
- **`Task.sleep(300ms)` を実際に待つテストは書かない**（遅く、CI で不安定になる）

### 5-2. 「古い応答が新しい結果を上書きしない」（AC-17 / BR-004）をどう起こすか

`StubHTTPClient` に **応答を保留し、任意の順で解放できる口**を持たせる。

```swift
let stub = StubHTTPClient()
stub.enqueue(for: "swi", response: .success(pageA), release: .manual)
stub.enqueue(for: "swift", response: .success(pageB), release: .manual)
vm.query = "swi";   await vm.waitForRequest()
vm.query = "swift"; await vm.waitForRequest()
stub.release("swift")   // 新しいほうを先に返す
stub.release("swi")     // 古いほうを後から返す
#expect(vm.state.items == pageB.items)   // ← 上書きされていない
```

**この解放順の制御が無いと AC-17 は書けない**（実装が正しくても偶然緑になる）。

### 5-3. 外部依存の扱い（2026-09-06 に改めた）

もともとは「読者が `swift test` を打つまでの障害を無くす」ために**依存ゼロ**にしていた。
**M5 で `ViewInspector` を1つだけ入れた**（[05 D-18](05-decisions.md)）。

- **入れた判断の根拠**: View の 16 件は「State に出ているのに画面に出ていない」を狙うものであり、
  **これを検出できないまま「TS は通っている」と書くほうが、依存が1つ増えるより悪い**
- **入れた範囲**: 3つの Feature のテストターゲットだけ。`Sources/` からは見えない。
  **`swift package resolve` が1回走るだけで、読者の手順は変わらない**
- `combine-schedulers` は入れていない。debounce は `scheduler` を注入して
  `.immediate` 相当に置き換えられるので、依存を足さずに決定的にできた（5-1）
- `swift-snapshot-testing` も入れていない。理由は [05 D-18](05-decisions.md) にある
  — **レイアウトを変えるたびに全件が赤になる**のは [D-13](05-decisions.md) の逆である

## 6. 「緑であること」を信用しない手順（参照元PJの学習の移植）

1. **実装が先に完成したテストは、最初から緑になる。** その状態では
   「そのテストが落ちうる」ことが証明されていない
2. よって、**書いたテストは実装を1箇所壊して赤になることを確認してから完了とする**（変異検証）
3. 壊す対象は**「その AC が縛る振る舞い」**であって、実装の置き場ではない
   （例: AC-17 なら世代番号の比較を消す。ファイルを丸ごと消すのは検証にならない）
4. 変異は **`git worktree` の隔離コピーで当てる**（作業ツリーの未コミット変更を巻き込まないため）
5. **死ななかった変異は記録に残す**。「テストが足りない」のか「その層からは観測できない」のかを
   その場で判定し、後者なら**どの層でなら観測できるか**を書く

> 参照元PJでは、この手順で **AC が1件も無い経路**（成否どちらに倒す実装でも全テストが緑になる箇所）が
> 実際に見つかっている。**変異検証は仕様の穴を見つける道具でもある**。

### 6-1. 実施の記録（2026-09-06・M5 で足した View 層 17 件）

| 当てた変異 | 死んだ TS |
|---|---|
| 説明が `nil` でも `Text` を出す | TS-49 |
| スケルトンを6行から5行にする | TS-48 |
| `topics` が空でもトピックの行を出す | TS-75 |
| ☆ / ★ のラベルを状態によらず固定にする | TS-101 |
| 数値バッジのラベルを数字だけにする | TS-102 |
| 行タップの結線（`onSelectRepo`）を外す | TS-51 |
| `.debounce` を丸ごと外す | TS-26 |
| `.debounce` を `.delay` に替える（遅れるが束ねない） | TS-26 |

**死ななかった変異が1つある。**

- **`debounceInterval` を 0 にしても、どのテストも赤にならない。**
  `scheduler` が `.main` なので、**同じ turn の中で3回代入しても、0 秒の debounce は最後の1つに束ねる**。
  つまりこれは「テストが足りない」のではなく、**振る舞いが変わっていない**（等価変異）である
- 間隔そのものが効いていることを見たいなら、**turn をまたいで代入する**テストが要る。
  ただしそれは「時間を待つテスト」になり、[§5-1](#5-1-debounce-をどうテストするか) と正面から矛盾する。
  **入れないと決めた。**

### 6-3. M2〜M4 に当てた（2026-09-06）

M5 の View 層に続いて、**先に書かれていた 111 件**にも当てた。
`git worktree` の隔離コピーで行っている（手順の 4）。

| 当てた変異 | 死んだ TS |
|---|---|
| 403 の `x-ratelimit-remaining` を見ずに常に `unknown` にする（AC-31） | TS-9・10・11・45・46・64 |
| `page` を常に 1 で要求する（AC-22） | TS-4・39・40・41 |
| 空白だけの検索語でも Repository を呼ぶ（AC-5） | TS-19・20 |
| `hasMore` が false でも次ページを要求する（AC-24） | TS-23 |
| 取得済み 1000 件の上限を見ない（AC-25） | TS-22 |
| `removeDuplicates()` を外す（AC-4） | TS-27 |
| 世代番号で古い応答を弾かない（AC-17 / BR-004） | TS-29・35 |
| キャンセルを失敗として表示する（AC-18） | TS-36 |
| 初期表示があっても `partial` から始めない（AC-1） | TS-58・60 |
| 取得失敗を `partial` にせず全部 `failed` にする（AC-9） | TS-60 |
| お気に入りの並びを古い順にする（AC-2） | TS-80 |

| **前の検索を `cancel()` しない（AC-16）** | **なし → §6-3-1** |
| 変更を購読者へ通知しない（BR-010） | TS-70・84・90・93・98・99・100 ／ **最初は赤ではなく「止まったまま」だった**（§6-3-2） |

#### 6-3-1. `cancel()` を消しても、誰も赤にならなかった

**AC-16（新しい検索が始まったら前の検索を止める）を観測しているテストが無かった。**

TS-34 は「新しい結果が残る」ことしか見ておらず、**世代番号（BR-004）だけでも緑になる**。
つまり TS-34 は AC-17 の二重掛けであって、AC-16 の観測点ではなかった。
放っておくと、**止め損ねた要求がレート制限（未認証は検索 10 回/分）を食い潰しても誰も気づかない**。

- **どの層で観測できるか**: Repository より外側では見えない。**スタブが「キャンセルされた」ことを覚える**必要がある
- **やったこと**: `StubHTTPClient` に `cancelledKeys` を持たせ、**TS-34b** を足した。
  変異を当て直すと TS-34b だけが赤になることを確認している

#### 6-3-2. 通知を止めたら、テストが赤ではなく「止まったまま」になった

購読者への `yield` を消したところ、**`swift test` が10分経っても終わらなかった**。
`await iterator.next()` は通知が来なければ永久に待つためで、当時
**時間制限を付けたテストが1つも無かった**。

- **これは「テストが無い」より悪い。** CI ではジョブの上限まで回り続け、
  何が壊れているかも分からない
- **やったこと**: ストリームを待つ4件に `.timeLimit(.minutes(1))` を付けた。
  さらに TS-34b では、**保留した要求を必ず `release` してから終わる**ようにした
  （止め損ねる実装だと、解放されない要求がテストを跨いで残る）
- **付けた後に同じ変異を当て直すと、止まらずに TS-70・84・90・93・98・99・100 が赤になる。**
  「止まったまま」と「7件が赤」では、直すときに分かることがまるで違う

> **変異検証は「テストが足りているか」だけを見る道具ではない。**
> ここでは、**壊れたときの落ち方**（赤か・ハングか）まで一緒に見えた。

### 6-2. 変異検証が、時間に依存したテストを1つ暴いた

変異を当てている最中に、**TS-26 が1度だけ落ちた**。当てた変異とは無関係な箇所である。

原因は、`await settle()`（固定 150 ms のスリープ）だけで
「debounce が明けて要求が飛んだ」ことを待っていたためで、
**負荷がかかると 150 ms では足りない**。「時間そのものを待つテストにはしない」（§5-1）が守れていなかった。

- **直し方**: 肯定（1回来た）は `waitUntil` で待ち、**否定（それ以上来ない）だけを `settle` で見る**
- 同じ形をしていた TS-35・TS-36・TS-40・TS-42 も直した
  （純粋な否定だけを見ている TS-24b・TS-27・TS-29 はそのままでよい）
- **確認**: `yes` を4本回して負荷をかけた状態で 10 回連続で緑になることを見た

> **「たまたま緑」は、変異検証の副産物として見つかることがある。**
> 同じ実装に対して何十回もテストを回すのは、この手順以外ではまず起きない。

## 7. TS 一覧（AC との対応）

**層**: R=Repository / U=UseCase / V=ViewModel / W=View / I=統合。
**※ は View を立てて見る 16 件**（[§3](#3-view-をテストする3項目例外)の3項目）。
うち **TS-94 の1件だけが未実装**であり、理由は §3-1 にある。

> **2026-09-06 に2回数え直した。**
> 1回目（M1 の締め）で、実装側にあって表に無い **TS-24b を1件見つけ、表に足した**
> （`hasMore` が false のときに要求しないことを ViewModel 層で見る test が、
> 採番だけされて表に載っていなかった）。**まさにこの節が想定していた「件数は合っているが
> 中身が違う」の実例**である。数え方は次のとおりで、いずれも実体から数えている。
>
> 2回目（M5 の締め）で View 層 15 件と、アクセシビリティの TS-101・TS-102 を足した。
>
> ```bash
> # AC は PRD ごとに数える（AC-1 は3つの UC すべてに在るので、まとめて sort -u すると潰れる）
> for f in docs/prd/*.md; do grep -ohE '\bAC-[0-9]+[a-z]?\b' "$f" | sort -u | wc -l; done
> grep -oE '^\| TS-[0-9]+[a-z]?' docs/04-test-strategy.md | sort -u | wc -l # TS（定義）
> grep -roh '@Test("TS-[0-9]*[a-z]*' Tests | sort -u | wc -l                # TS（実装済み）
> ```
>
> **実装済みは `@Test(...)` の名前から数える。** 本文コメントに書いた TS 番号まで拾うと、
> 「触れているだけの番号」が実装済みに化ける — 実際、1回目は
> `/// UC-003 の View 層（TS-94〜TS-97）` というコメントのせいで、
> **未実装の TS-94 が実装済みとして数えられていた。**

**未実装は TS-94（スワイプ削除）の1件だけ**であり、
**「書いていない」のではなく「この道具では観測できない」**である（§3-1 に理由を書いた）。
定義と実装の差をここに出しておくのは、**件数だけ書くと全部通っていると読まれる**ためである。

- **AC を持たない TS が 8 件ある**（TS-5・TS-12〜TS-15・TS-17・TS-101・TS-102）。
  前の6件は [02 §4 のエラー写像表](02-github-api.md)を、
  後の2件は [05 D-19](05-decisions.md) を正とする検証であり、**意図的に AC を持たない**
  （どのUCにも属さない横断の規約であるため）。**空欄にせず、対応欄に正の場所を書く**
- **数え直しは実体（本ファイルの表）から行う。** 件数だけを引き算で更新しない
  — 参照元PJで、廃止1件と新設1件が相殺して「件数は合っているが中身が違う」状態が実際に起きている
