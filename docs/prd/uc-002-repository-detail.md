# UC-002 リポジトリの詳細を見る

|---|---|

| **AC** | 21 件 ／ **BR** 3 件 ／ **未解決 Q** 0 件 |

---

## 1. 目的

一覧では見えない情報（ライセンス・トピック・ウォッチャー実数・Issue 数・アーカイブ状態）を見せる。
あわせて、**「レート制限が厳しい API で、失敗しても白い画面にしない」**作法を示す。

## 2. スコープ / 非スコープ

**スコープ**: 詳細の取得と表示、一覧由来の情報での先行描画、失敗時の部分表示、
お気に入りトグル、GitHub を Safari で開く。

**非スコープ**: README の表示、コントリビュータ一覧、Issue/PR 一覧、アプリ内 WebView、
詳細のキャッシュ。

---

## 3. Business Rule

| ID | 規則 | 根拠 |
|---|---|---|
| **BR-007** | 一覧から来たときは、**API を待たずに** summary の内容を描く | 03 §B-2 |
| **BR-008** | 詳細の取得に失敗しても、**summary 由来の表示は消さない** | 同上 |
| **BR-009** | ウォッチャー数として出すのは `subscribers_count` であり、`watchers_count` は使わない | 02 §2-2（検索の `watchers_count` は star と同値） |

---

## 4. 受け入れ条件（AC）

### 4-1. 表示

- **AC-1**: 検索一覧から遷移したとき、**API の応答を待たずに**アバター・`full_name`・説明・
  スター数・フォーク数・言語が表示されている
- **AC-2**: 詳細の取得が成功すると、ウォッチャー数・Issue 数・ライセンス・トピック・更新日が加わる
- **AC-3**: ウォッチャー数は `subscribers_count` の値である（BR-009）
- **AC-4**: `license` が `null` のとき、「ライセンス なし」と表示される（**行は残す**）
- **AC-5**: `topics` が空のとき、トピックの行そのものが表示されない
- **AC-6**: `archived` が true のとき「アーカイブ済み」バッジが出る
- **AC-7**: `fork` が true のとき、フォークである印が出る
- **AC-8**: 「GitHub で開く」を押すと `html_url` が外部ブラウザで開く（アプリ内 WebView は使わない）

### 4-2. 失敗

- **AC-9**: 一覧から来た画面で詳細取得が失敗したとき、**AC-1 の表示は残ったまま**、
  下部に「詳細を読み込めませんでした」と再試行が出る（BR-008）
- **AC-10**: お気に入りから来た画面（summary を持たない）で失敗したとき、**画面全体がエラー表示**になる
- **AC-11**: 再試行を押すと、同じリポジトリの詳細をもう一度取得する
- **AC-12**: 404 のとき、「見つかりませんでした」が表示され、**再試行ボタンは出ない**
- **AC-13**: レート制限のとき、「あと N 分で再開できます」が表示され、再試行ボタンは出ない
- **AC-14**: 通信できないとき、専用の文言（「つながりませんでした」）が表示される

### 4-3. 生存期間とキャンセル

- **AC-15**: 詳細の取得中に画面を閉じたとき、進行中の Task は**キャンセルされる**
- **AC-16**: 画面を閉じたあとに応答が届いても、**状態の更新も画面の再表示も起きない**（クラッシュしない）
- **AC-17**: 同じ画面で再試行を連打しても、**同時に走る取得は1つだけ**である（前をキャンセルしてから始める）

### 4-4. お気に入り

- **AC-18**: 詳細画面の ☆ を押すと ★ になり、**検索一覧の同じ行も ★ に変わる**（UC-003）
- **AC-19**: 検索一覧側で外したとき、開いている詳細画面の ★ も**即座に** ☆ に戻る
- **AC-20**: お気に入りに追加するとき、**詳細取得の成否によらず**追加できる（summary があれば足りる）
- **AC-21**: summary を持たない入口（お気に入りタブ）から開き、かつ詳細取得に失敗した場合、
  ☆ の操作は**できる**（すでにお気に入りである状態から外せる）

## 5. 層ごとの責務

| 層 | このUCでやること |
|---|---|
| `RepoRepository` | `fetchDetail(owner:name:) async throws -> RepoDetail` |
| `FetchRepoDetailUseCase` | Repository を呼ぶだけ。**判断を持たない**（薄いことを許容する。UseCase を飛ばして Repository を触らせないため） |
| `RepoDetailViewModel` | 初期 State を summary から作る（BR-007）・取得・部分失敗の合成（BR-008）・お気に入りの購読 |
| `RepoDetailScreen` | 描くだけ |

> **薄い UseCase を作る理由**: 層を飛ばす例外を1つ許すと、そこが前例になる。
> 「UseCase が薄い」は設計の失敗ではなく、**このUCが単純である**という事実の反映である。
