## 1. 目的

キーワードから GitHub の公開リポジトリを見つけられるようにする。
**このUCが本サンプルの中核**であり、debounce・キャンセル・世代管理・ページング・
レート制限の扱いという「並行処理の難所」をすべてここに集めている。

## 2. スコープ / 非スコープ

**スコープ**: 検索語の入力と debounce、検索の実行、一覧表示、追加読み込み、
各状態（初期・読込中・成功・0件・失敗・レート制限）、一覧からのお気に入りトグル、詳細への遷移。

**非スコープ**: ソート順・言語での絞り込み UI（`sort`/`order` は送らない）、検索履歴、
検索語の保存、ユーザー検索・コード検索、オフライン時の結果キャッシュ。

## 3. Business Rule

| ID | 規則 | 根拠 |
|---|---|---|
| **BR-001** | 検索リクエストは**最後の打鍵から 300ms 経過してから**投げる | 未認証の Search API は 10 req/分（02 §3-1） |
| **BR-002** | 直前と同じ検索語では投げ直さない（`removeDuplicates`） | 同上 |
| **BR-003** | 新しい検索が始まったら、**進行中の検索と追加読み込みは必ずキャンセルする** | 01 §5-4 |
| **BR-004** | **応答が状態を書けるのは、それが最新の世代であるときだけ**。古い応答は捨てる | 01 §5-4（キャンセルだけでは足りない） |
| **BR-005** | `hasMore` は `items.count == per_page` かつ `取得済み < min(total_count, 1000)` | Search API の 1,000 件上限（02 §3-2） |
| **BR-006** | 追加読み込みの失敗は**一覧を消さない**。一時的な通知にとどめる | 03 §A-3 |

## 4. 受け入れ条件（AC）

### 4-1. 入力と debounce

- **AC-1**: 検索欄が空のとき、画面は `initial`（案内文）で、**API を1回も呼ばない**
- **AC-2**: 検索欄に文字を入れると、**最後の入力から 300ms 後に**検索が1回だけ始まる
- **AC-3**: 300ms 以内に続けて入力したとき、**API 呼び出しは1回だけ**である（打鍵の回数だけ呼ばない）
- **AC-4**: 直前と同じ文字列に戻ったとき（例: `swi` → `swif` → `swi`）、**同じ語での再検索はしない**
- **AC-5**: 前後の空白は取り除いてから検索する。**取り除いた結果が空なら `initial` へ戻す**
- **AC-6**: 検索語が空になったとき、進行中の検索は**キャンセルされ**、画面は `initial` に戻る
- **AC-7**: 検索語が空になった直後に、キャンセルされた検索の応答が届いても、**画面は `initial` のままである**

### 4-2. 検索の実行と結果

- **AC-8**: 検索中は**スケルトン行が 6 行**表示される（スピナーではない）
- **AC-9**: 成功して1件以上あれば、一覧が `full_name` / 説明 / スター数 / 言語 / 更新日 とともに表示される
- **AC-10**: 説明が `null` の行では、**説明の行そのものが表示されない**（空行を作らない）
- **AC-11**: 言語が `null` の行では、**言語の表示そのものが無い**
- **AC-12**: スター数は 1,000 以上のとき `67.0k` の形式で、1,000 未満はそのままの数値で表示される
- **AC-13**: 更新日は 7 日以内なら相対表記（「3日前」）、それ以前は `yyyy/MM/dd` で表示される
- **AC-14**: 成功して 0 件のとき、**検索語を含んだ**「“{query}” に一致するリポジトリはありません」が表示される
- **AC-15**: 検索は `q` `per_page=30` `page=1` だけを送る（`sort` と `order` は**送らない**）

### 4-3. キャンセルと順序（BR-003・BR-004）

- **AC-16**: 検索語 A の応答が返る前に検索語 B を入力したとき、**A の Task はキャンセルされる**
- **AC-17**: A の応答が B の応答より**後に**届いたとき、**画面には B の結果が残る**（A で上書きされない）
- **AC-18**: キャンセルされた検索が `CancellationError` / `URLError.cancelled` で終わったとき、
  **画面はエラー表示にならず、ローディングも解除されない**（次の検索が状態を持つ）
- **AC-19**: `URLError.cancelled` は `GitHubError` に写像されない（Repository はそのまま投げる）

### 4-4. 追加読み込み

- **AC-20**: 一覧の末尾から 3 行以内が表示されたとき、次のページを1回だけ取得する
- **AC-21**: 追加読み込み中も**既存の行は表示されたまま**で、末尾にインジケータが出る
- **AC-22**: 取得したページは既存の一覧に**追記**される（置き換えない）
- **AC-23**: 同じページを二重に要求しない（進行中は次の要求を無視する）
- **AC-24**: `hasMore` が false のとき、末尾に到達しても API を呼ばない
- **AC-25**: 取得済み件数が 1,000 に達したら `hasMore` は false になる（**1,001 件目を要求しない**）
- **AC-26**: 最終ページ（`items.count < 30`）を受け取ったら `hasMore` は false になる
- **AC-27**: 追加読み込みが失敗しても**一覧は消えず**、一時的な通知が出るだけである（BR-006）
- **AC-28**: 追加読み込み中に検索語が変わったら、そのページの結果は**捨てられる**（BR-004）

### 4-5. 失敗

- **AC-29**: 通信できないとき、「つながりませんでした」と**再試行ボタン**が表示される
- **AC-30**: 再試行を押すと、**同じ検索語で**もう一度検索する
- **AC-31**: レート制限（403/429 かつ `x-ratelimit-remaining: 0`）のとき、
  **「あと N 分で再開できます」が表示され、再試行ボタンは出ない**
- **AC-31b**: `x-ratelimit-reset` が無いときは、分数を出さず「しばらく待ってからお試しください」にする
- **AC-32**: レート制限中は、**自動での再試行を一切行わない**（打鍵による再検索は妨げない）

### 4-6. 一覧からの操作

- **AC-33**: 行の ☆ を押すと、その場で ★ に変わり、**お気に入りタブの一覧にも即座に現れる**（UC-003）
- **AC-34**: 行をタップすると詳細画面へ遷移し、**一覧が持っていた情報が即座に描かれる**（UC-002 AC-1）

## 5. 層ごとの責務

| 層 | このUCでやること |
|---|---|
| `RepoRepository` | `search(query:page:perPage:) async throws -> RepoPage`。DTO→Entity、HTTP→`GitHubError`、`hasMore` の算出（BR-005） |
| `SearchReposUseCase` | 検索語の検証（空・空白のみを弾く ＝ AC-5）→ Repository 呼び出し。**1ページ目専用** |
| `LoadMoreReposUseCase` | 次ページの取得。**現在の取得済み件数と `total_count` を受け取り、要求してよいかを判定**（BR-005・AC-25） |
| `SearchViewModel` | debounce（BR-001）・世代管理（BR-004）・Task のキャンセル（BR-003）・Entity→State 変換・エラー→文言 |
| `SearchScreen` / `RepoRowView` | State を描くだけ |

> **`hasMore` の判定を Repository と UseCase の両方に置かない**。
> Repository は「このページの応答から分かること」（`items.count == per_page`・`total_count`）を
> `RepoPage` に載せるだけ、**要求してよいかの判断は UseCase** に置く。
> 2箇所に判断を置くと、片方だけ直したときに矛盾する。

## 7. 決定の記録

- **なぜ 300ms か**: 100ms では打鍵中に投げてしまい 10 req/分に当たる。500ms は体感で遅い。
  **値は `SearchViewModel` の初期化引数**にして、テストでは 0 にできるようにする（`Task.sleep` を待たない）
- **なぜ `sort` を送らないか**: best match が最も期待に近く、ソート UI は本サンプルの評価軸に寄与しない。
  送らないことを AC-15 で**固定する**（あとから足すときに AC を消す必要があるので、変更が可視になる）
